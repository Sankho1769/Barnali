# BARNALI database access-control matrix

This matrix was built from V1/V2, the proposed additive V3 migration, and the current JDBC calls in the authentication, community, and admin services. V1 and V2 remain unchanged. This is source-level work only: V3 has not been applied, and no PostgreSQL policy or function behavior has been tested against a live or local PostgreSQL server.

## Access model

- The Spring transaction manager sets `barnali.user_id` transaction-locally from the server-side `AppPrincipal`, never from request JSON or a query parameter. A missing principal or an explicit anonymous authentication scope sets the empty value. PostgreSQL transaction-local settings revert on both commit and rollback; the Hikari connection-init setting establishes an empty baseline as a second safeguard.
- RLS is the default for ordinary public/member/admin table reads and writes. Policies derive ownership from `barnali.current_actor_id()` and administrator capabilities from `barnali.actor_has_permission(...)`; they do not accept an actor id or role from the request.
- Narrow, fixed-search-path `SECURITY DEFINER` functions are needed only where a pre-authentication path must access protected credentials/tokens, where a multi-step operation must be atomic, or where a safe aggregate must be returned without exposing its contributing rows.
- The function owner is the migration/table owner (`barnali_migrator`), not the runtime principal. The migration credential is therefore a high-trust offline credential and must not be configured for the API. Runtime calls are limited by function EXECUTE grants and the function code. All application roles remain `NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE` and receive no membership in the migration role.
- The owner-provisioning connection is a separate `barnali_provisioner` login with schema `USAGE` and EXECUTE on only the read-only readiness function and one-shot owner function. It receives no table or sequence privileges. The function atomically consumes a persistent guard row; deleting an owner later does not reset that guard.
- `SECURITY DEFINER` routines must be schema-qualified internally, use `SET search_path = pg_catalog, barnali, pg_temp`, revoke default `PUBLIC` EXECUTE, and validate their arguments. The role that owns these routines can bypass ordinary RLS as table owner; it is never an API role. The Supabase `public.rls_auto_enable()` event trigger described in earlier diagnostics is a separate database-owned component and is not changed or executed by this project.

## Permission-to-query map

The database helper must mirror `PermissionMatrix` exactly:

| Role | Permission-restricted operations |
|---|---|
| OWNER | All current admin reads/writes, including team management. |
| SUPER_ADMIN | Overview, analytics, users/suspension, room read/manage, report read/resolve, team read, audit read; no team management. |
| MODERATOR | Overview, user read/suspension, room read, report read/resolve, audit read. |
| ANALYTICS_VIEWER | Overview, analytics, room read. Analytics is aggregate-only. |
| SUPPORT_ADMIN | Overview, user read, audit read. |

Controller annotations remain an HTTP authorization layer. RLS/function checks are a second server-side database boundary and must not replace controller checks. The transaction identity setting is supplied by trusted server code; it is not cryptographic database authentication and does not protect against a compromised API process or arbitrary SQL executed with the runtime credential. `SECURITY DEFINER` functions and owner-rights views rely on the migration owner; their bodies, fixed search paths, grants, and results require PostgreSQL testing before deployment.

## PostgreSQL validation still required

This matrix is source-derived. Without PostgreSQL, the following remain unverified: exact V3 syntax and dependency behavior; Supabase event-trigger interaction; view/function ownership and ACLs after Flyway; `SECURITY DEFINER` execution under the actual provisioned role memberships; RLS behavior on pooled sessions for commit and rollback; identity/sequence privileges; role creation/ownership grants; and all cross-role integration cases. Keep the Testcontainers profile for those checks. Never use production credentials for them.
